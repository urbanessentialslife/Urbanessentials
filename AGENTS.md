# Shopify Hydrogen development

This storefront is scaffolded from Shopify's Hydrogen skeleton template. See the README for framework-specific details.

Use the [Shopify AI Toolkit](https://shopify.dev/docs/apps/build/ai-toolkit) for all Shopify API and platform work. If missing, install it in the agent host per that page (or `npx skills add Shopify/shopify-ai-toolkit --list` for skill-compatible hosts).

## Stack

- **Framework:** Shopify Hydrogen 2026.4.x on React Router 7 (framework mode), server-rendered on every request — no client-only rendering.
- **Deploy targets:** Shopify Oxygen (Cloudflare Workers) is primary; a Vercel Node.js target also exists (`build:vercel`, `server/vercel.ts`). The two share `app/entry.server.tsx` but resolve platform-specific render logic through a Vite alias — see `app/lib/renderPlatform.oxygen.tsx` / `renderPlatform.vercel.tsx` and the `resolve.alias['~/lib/renderPlatform']` entry in `vite.config.ts`. Oxygen's Worker build has no code-splitting and no Node built-ins, so platform-specific code must go through that alias, never a runtime `if (process.env.VERCEL)` branch.
- **Styling:** Tailwind v4. No separate design-system package — brand color tokens are repeated inline as hex literals: `#241a16` (ink/text), `#f4f0e8` (parchment background), `#a69686` (muted accent), `#c9c2b8` (borders), `#b89b6a` (gold accent). Match these exactly when styling new UI rather than inventing new tones.
- **Animation:** GSAP + ScrollTrigger for scroll-linked sequences (see `app/components/visual/Showroom`, `ProductTransitionShowcase`, `ProductVideoScrubStage`). Always gate motion behind `window.matchMedia('(prefers-reduced-motion: reduce)')` and scope GSAP work in a `gsap.context()` that gets `.revert()`-ed on cleanup — React 18 StrictMode's double-mount will otherwise leave stale ScrollTrigger pins/spacers behind.
- **Data:** Storefront API (public, customer-facing catalog/cart, *and* the classic password-based customer account mutations — see below) via Hydrogen's built-in client. A separate hand-rolled Admin API client (`app/lib/admin.server.ts`) exists only for the one thing the Storefront API can't do: subscribing an email to marketing without creating a full customer record.
- **Codegen:** `npm run codegen` / `shopify hydrogen build --codegen` statically parses every `` #graphql `` -tagged template literal against the Storefront API schema. This does **not** run during `npm run typecheck` (plain `tsc`), so a codegen-breaking mistake (JS template interpolation inside a tagged query string, or tagging an Admin API query with `#graphql`) is invisible until an actual build runs. Always run the real build after touching any GraphQL query, not just typecheck.

## Folder structure

- `app/routes/` — one file per route (React Router v7 flat-file convention: `products.$handle.tsx`, `account.orders.$id.tsx`, etc.). Each route owns its own GraphQL queries as `#graphql`-tagged template literals at the bottom of the file.
- `app/components/visual/` — the site's actual custom-designed UI ("the showcase"), organized by area (`Product/`, `Shop/`, `Common/`, `Showroom/`). This is what every route renders.
- `app/components/*.tsx` (top level, e.g. `Header.tsx`, `Footer.tsx`, `CartMain.tsx`, `AddToCartButton.tsx`) — **leftover Hydrogen skeleton scaffold, not used anywhere.** The real header/footer/cart are `ShowcaseHeader`/`ShowcaseFooter`/`ShowcaseCartDrawer` under `visual/Common/`, wired up in `app/components/PageLayout.tsx`. Don't build on the top-level ones; if you're touching cart or header/footer behavior, it's in `visual/Common/` and `ShowcaseCartContext.tsx`.
- `app/context/ShowcaseCartContext.tsx` — the real cart implementation. The shopping list itself is local React state (instant add/remove, persisted to `localStorage`), submitted as one real Shopify cart mutation only at checkout time, then redirects to Shopify's hosted checkout. Not a live-synced Storefront cart the way the skeleton's `CartMain.tsx` assumes.
- `app/data/showcaseProducts.ts` — hand-curated marketing copy/assets (taglines, spec sheets, per-finish cutout images and videos) for the products the showcase was originally designed around.
- `app/lib/showcaseCommerce.ts` — merges that curated template data with the live Shopify catalog (real price/stock/variant IDs) by matching variant names, so admin price/stock edits go live immediately while bespoke visuals stay put. Any product an admin adds beyond the curated set still renders, through a generic fallback mapper.
- `app/lib/*.server.ts` — server-only modules (the `.server` suffix is enforced by the bundler, not just convention — these are stripped from client bundles).
- `app/lib/customerAuth.server.ts` — the storefront's actual customer auth: classic Storefront API mutations (`customerCreate`, `customerAccessTokenCreate`, etc.), with the resulting access token stored in the app's own session cookie (see `session.ts`). Every account route reads/writes through this, not through `context.customerAccount`.
- `docs/` — setup notes for things that require live Shopify Admin configuration (metafield definitions, a "Customization Fee" billing product, etc.) that can't be expressed in code alone.

## Conventions and known gotchas

- **Customer accounts are classic (email + password), not the new OAuth-hosted Customer Account API.** `context.customerAccount` is still wired up by `createHydrogenContext` (Hydrogen requires it) but is **unused** — the account routes (`account_.register.tsx`, `account_.login.tsx`, `account.profile.tsx`, `account.addresses.tsx`, `account.orders*.tsx`) all go through `app/lib/customerAuth.server.ts`'s classic `customerCreate`/`customerAccessTokenCreate`/`customerUpdate`/`customerAddress*` mutations instead, so registration can collect name/phone/address up front and login is real email+password — both against real Shopify customer records, visible in Admin. This was a deliberate move away from the OAuth-hosted flow (which is passwordless by design and doesn't support a custom-branded form); don't move it back without checking this is still wanted. Two schema quirks to remember if you touch this: the classic `Order` type has no `confirmationNumber` field (only the newer Customer Account API does — see `orderFilters.ts`), and `MailingAddressInput` uses `country`/`province`, not the newer API's `territoryCode`/`zoneCode`.
- **The internal "Customization Fee" product must stay invisible to shoppers.** It's a real Shopify product (has to be, to carry real priced variants for the personalization surcharge — see `docs/customization-setup.md`), auto-added as a second cart line at checkout. `mapShowcaseCatalog()` in `showcaseCommerce.ts` filters it out of the public catalog, and the sitemap route strips it from the generated XML — both must stay in sync if the handle ever changes.
- **Storefront/Customer Account API version is not explicitly pinned** — it follows whatever `@shopify/hydrogen`'s installed version defaults to (currently `2026-04`, set in `node_modules/@shopify/hydrogen`). The Admin API version in `admin.server.ts` **is** explicitly pinned (`ADMIN_API_VERSION`) and needs bumping roughly every 12 months as Shopify retires old versions — check it isn't stale before assuming the Admin integration works.
- **Returns** (`routes/returns.tsx`) file Shopify return *requests* via the Admin API (`getReturnableOrder` / `submitReturnRequest` in `admin.server.ts`), re-verifying order number + email server-side on submit — never trust fulfillment-line IDs or quantities from the browser.
- **`SHOPIFY_ADMIN_API_TOKEN` is required for newsletter signup to function** — without it, `subscribeToNewsletter()` throws immediately. Never let that error's raw message reach the client (it contains internal setup instructions); log it server-side and return a generic customer-facing message instead.
- Buyer country is per-visitor: `app/lib/context.ts` reads it from the session (`COUNTRY_SESSION_KEY`, set by `routes/api.country.tsx` from the footer selector), defaulting to `DEFAULT_COUNTRY` (`IN`) in `app/lib/i18n.ts`. The selector only renders when Shopify Markets has >1 country. Every catalog/cart query must keep `@inContext(country: $country, language: $language)` or it will silently show primary-market prices. Format prices with `formatAmount()` from `app/lib/money.ts`, never a hardcoded `toLocaleString('en-IN')`.
- Prefer Hydrogen's `<Image>` component over a raw `<img src={shopifyCdnUrl}>` for anything served from Shopify's CDN — it adds width-based CDN query params and `srcset` automatically. Several of the custom `visual/` components currently use raw `<img>` for curated local assets (by design, they're not Shopify-hosted) but fall through to raw Shopify CDN URLs for any admin-added product outside the curated set, which loses that optimization. Worth fixing incrementally as you touch those files.
- **`app/styles/reset.css` must never gain bare element-selector rules for tags the design system styles via Tailwind classes** (`section`, `h1`–`h6`, `a`, `fieldset`, `form`, `input`'s `border`, etc.). It used to — leftover Hydrogen-skeleton styling, unlayered plain CSS — and because Tailwind v4's generated output is wrapped in `@layer`, an unlayered rule beats *any* Tailwind utility class regardless of specificity or source order. That silently zeroed every `<section>`'s padding, shrank every `<h2>` to 19.2px, forced every link to black with an underline on hover, flattened every `<fieldset className="grid ...">` to a single column, and stripped every input's border — sitewide, for what was probably years, without ever throwing an error. If you need a true baseline reset for unclassed CMS-injected HTML (blog/page rich text), scope it under the content's own wrapper selector (e.g. `.prose h2`), never a bare tag selector in a globally-loaded stylesheet.
